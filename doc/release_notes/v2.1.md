# PaScaL_TDMA 2.1 release notes

PaScaL_TDMA 2.1 supersedes version 2.0 as the current GPU-oriented release. It
preserves the original distributed reduction, reduced-system solve, and local
reconstruction method while reformulating the CUDA Fortran kernels and
communication path for modern multi-GPU systems.

## Published version 2.1 changes

The PaScaL_TDMA 2.1 article reports four principal implementation changes from
version 2.0:

- shared-memory buffering is replaced by register-resident elimination
  kernels;
- adjacent CUDA threads process adjacent tridiagonal lines for coalesced
  global-memory access;
- assumed-shape kernel arrays are replaced by fixed-bound arrays and explicit
  scalar arguments to avoid implicit descriptor transfers at launch; and
- the coefficient fields used to assemble the reduced system are packed into
  a consolidated all-to-all exchange, with the unit diagonal reconstructed
  locally.

These changes preserve the numerical structure of the original five-step
PaScaL_TDMA method. See the [PaScaL_TDMA 2.1 article](https://doi.org/10.1016/j.cpc.2026.110120)
for the hardware- and problem-specific performance and application studies.

## Communication boundary in this source tree

The article uses `MPI_Alltoall` as the algorithm-level description of the
consolidated exchange. The source in this release calls `MPI_Alltoallv` and
retains two collective phases for each distributed solve:

1. a forward exchange containing packed reduced `A`, `C`, and `D` fields; and
2. a backward exchange returning reduced interface `D` values before the full
   local solution is reconstructed.

Consequently, a consolidated all-to-all means that separately exchanged
coefficient fields are consolidated during reduced-system assembly. It does
not mean that the complete solver performs only one collective call.

## Repository extensions

The publication and version 3 program archive describe the CUDA Fortran
implementation. This repository additionally includes:

- a CUDA C++17 port of the same distributed solver flow;
- an optional CUDA C++ host-staging MPI path selected with
  `PASCAL_TDMA_MPI_MODE=host`;
- phase-profiled Fortran and C++ solve entry points;
- corresponding example and sweep drivers; and
- an engineering Study dataset and report.

These additions are repository extensions. They are not implementations or
benchmark results reported in the PaScaL_TDMA 2.1 article.

## Breaking changes from version 2.0

- The CUDA Fortran plan type changes from `ptdma_plan_many_cuda` to
  `ptdma_plan_cuda`.
- The primary lifecycle changes from `PaScaL_TDMA_plan_many_create_cuda`,
  `PaScaL_TDMA_many_solve_cuda`, and `PaScaL_TDMA_plan_many_destroy_cuda` to
  `pascal_plan_create`, `pascal_solver`, and `pascal_plan_clean`.
- The coefficient interface changes from version 2.0 three-dimensional arrays
  to system-contiguous `(nsys, nrow)` arrays.
- The version 2.0 CPU implementation is not included in the version 2.1
  working tree.
- The version 2.0 cyclic CUDA solve entry point is not included; the version
  2.1 implementations in this repository are non-cyclic.
- The previous heat-transfer example is replaced by solver-focused Fortran and
  C++ examples and profiling drivers.

The `v1.0` and `v2.0` tags continue to preserve the earlier source trees and
documentation.

## Operational contract

Both version 2.1 implementations operate on double-precision arrays with the
flat storage rule

```text
offset(sys, row) = sys + row * nsys
```

`D` contains the right-hand side on entry and the solution on return. A
one-rank solve modifies `C` and `D`; a distributed solve modifies `A`, `C`, and
`D`. `B` is read but not modified. Restore all modified inputs before solving
the same original mathematical system again.

For multiple ranks, every rank requires `nrow >= 2`, and the current
reduced-system partition requires `nsys >= number of ranks`.

## Requirements

- NVIDIA GPU and compatible driver;
- NVIDIA HPC SDK with CUDA Fortran support;
- CUDA Toolkit and C++17 support for the CUDA C++ port;
- MPI Fortran and C++ compiler wrappers; and
- CUDA-aware MPI for CUDA Fortran and for the default CUDA C++ device-buffer
  mode.

Only the CUDA C++ port supplies an explicit host-staging fallback.

## Validation boundary

The publication reports its CUDA Fortran performance under the configurations
defined in the article; those results are not universal performance
guarantees.

The checked-in repository Study is a separate engineering dataset. Its current
curated results contain CUDA C++ rows only. Correctness is recorded after
iteration 0, and later timed iterations operate on arrays transformed by
earlier in-place solves. The Study therefore does not establish a
Fortran-versus-C++ performance comparison or repeated independent-solve
timing. See [the Study documentation](../study/README.md) and
[report](../study/report_cuda_cxx_porting_tdma_solver_study.md) for the complete
protocol.
